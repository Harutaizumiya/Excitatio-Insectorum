# 教师端迁移微信小程序 PRD

版本：v0.2 实施稿（保留未决项） ｜ 日期：2026-10-08 ｜ 产品：Excitatio Insectorum

需求来源：[分析教师端迁移微信小程序的可行性](codex://threads/01a0eb16-6edb-76f2-94fb-38fb2c72f689)。代码核对基线：`dev` / `703c152`。本文定义产品需求，不代表相关能力已实现或已通过微信审核。

## 1. 背景与决策状态

为了适应国内教师使用习惯，将现有教师移动端迁移至微信小程序，使教师通过微信进入课堂操作，并在首次完成身份绑定后使用同一微信账号再次登录。

| 状态             | 内容                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| 用户已明确       | 教师移动端迁移至微信小程序；希望通过微信身份识别对应教师                                                |
| 本稿建议         | 微信身份绑定已有教师账号；首期迁移现有课堂业务；网页教师端与小程序分阶段并行                            |
| 技术建议，待验证 | 独立 `apps/teacher-miniprogram`；Taro 4 + React 18 + TypeScript；复用现有后端，适配网络、存储和实时通信 |
| 必须评审         | 邀请是否增加班主任确认、跨班重复账号处理、账号恢复权限、班主任是否纳入首批、网页端退场条件              |

除“用户已明确”和下列本轮确认外，本文新增的流程和指标仍为评审建议。未决事项不应被开发者自行当作已批准规则。

2026-10-08 实施确认：教师持有效小程序专用邀请，经微信登录并确认后直接绑定，不增加班主任二次审批。禁止自动合并历史账号、覆盖已有绑定或自动换绑；发生冲突时联系班主任人工核验。Web 教师端继续保留。本轮代码采用独立 Taro 4 / React 18 小程序，真实微信身份、正式域名和真机闭环仍须按第 9 节验证。实现及验收边界见 [实施记录](教师端小程序迁移实施记录.md)。

## 2. 目标与范围

### 2.1 产品目标

1. 已绑定教师再次进入小程序，无需重新领取邀请即可恢复本人有权访问的课堂。
2. 完整保留教师端的学生查找、座位查看、积分事件登记、流水与撤销、随机点名、远程喊话能力。
3. 沿用教师账号、班级关系及历史数据，迁移不改变积分归属、历史操作者和撤销权限。
4. 微信后台挂起、弱网和重复点击时，不产生重复计分、错误绑定或跨班操作。

### 2.2 首期范围

| 端              | 首期工作                                                                          |
| --------------- | --------------------------------------------------------------------------------- |
| 微信小程序      | 微信登录、绑定确认、课堂首页、积分登记、流水、点名、喊话、账号与会话状态          |
| 班主任 Web 后台 | 现有教师的迁移邀请、小程序码、绑定状态、邀请撤销/重发；恢复流程按最终授权方案实现 |
| 后端            | 微信凭证交换、身份绑定、邀请安全、会话接入及必要的幂等与恢复能力                  |
| 班级大屏        | 保持现有业务协议和隐私边界；参与点名、喊话与回复联调                              |
| 教师 Web        | 并行期继续可用，增加迁移入口；不在首版上线当天直接删除旧入口                      |

首期不迁移班主任完整管理后台、大屏页面或座位编辑；不增加家长/学生账号、支付、聊天、微信订阅消息、离线计分、跨平台小程序发布。头像、昵称和手机号不作为课堂使用的强制条件。班主任进入小程序的具体范围见第 12 节。

## 3. 现状与迁移基线

| 现有事实                                                                          | 迁移要求                                                        |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `/teacher`、`/teacher/history` 位于 Vite/React Web 应用，依赖网页组件、路由和存储 | 重做小程序页面与运行时适配，不能直接打包 Web 页面作为完成迁移   |
| `User` 为教师主体，`ClassTeacher` 表示班级关系，`Session` 表示会话                | 微信身份映射到原 `User.id`，权限继续来自服务端班级关系          |
| 当前新增任课教师会同时创建新 `User`                                               | 同一真人跨班可能存在多个账号，不得按姓名、学科或昵称自动合并    |
| 邀请有效期为 24 小时，消费后创建 `TEACHER_MOBILE` 会话；预览只返回班级和班主任    | 新增教师姓名、学科等确认信息，区分 Web 邀请消费与小程序绑定用途 |
| 课堂已使用积分事件表单，可多选学生                                                | 迁移事件登记业务，不能仅按旧设计稿实现快捷规则按钮              |
| 流水包含全部、本人、已撤销筛选；后端按角色限制撤销                                | 保留现有可见范围和后端权限，不额外扩大或收缩                    |
| 实时客户端为浏览器 Socket.IO；喊话面板当前另有 3 秒轮询                           | 验证小程序协议适配，前台刷新与重连补拉必须具备                  |
| 当前撤销任课关系会吊销该用户全部会话                                              | 多班级方案必须评审这种影响，不能承诺只退出单班而不修改后端      |

`docs/06-ui-design.md` 的部分内容与代码存在差异，例如旧积分表单及喊话自定义回复限时。迁移以实际服务端契约、当前实现及已确认业务变更为准；这些差异应在实施时同步修订，不以迁移为由回退业务。

## 4. 角色、身份与权限

### 4.1 角色

- 任课教师：使用本人获授权班级的课堂功能，查看允许的流水，撤销本人可撤销的记录。
- 班主任：在现有后台维护本班任课关系、发放/撤销迁移邀请、协助核实错误绑定。
- 未绑定微信用户：仅访问登录、合法邀请预览及绑定状态，不得读取学生名单和积分。
- 已解绑、账号停用或关系失效的用户：不得继续利用缓存会话或实时连接访问失效权限。

### 4.2 身份规则

采用“微信身份 → 系统教师账号 → 班级关系”的授权链。登录凭证由服务端向微信校验；客户端提交的 OpenID、教师 ID、角色和班级 ID 均不能直接成为授权依据。

建议以 `(AppID, OpenID)` 标识微信身份，绑定既有 `User.id`；不依赖一定存在的 UnionID，不使用昵称、头像、姓名匹配教师。AppSecret 和 `session_key` 不下发、不写入客户端日志。微信登录成功仅证明微信账号身份，仍须完成教师绑定。

首期默认建议一个微信身份对应一个教师账号，同一小程序内一个教师账号同时只绑定一个微信身份。一个账号可按现有有效关系访问多个班级，但不自动解决历史上的多个 `User`。

| 冲突                             | 处理                                                 |
| -------------------------------- | ---------------------------------------------------- |
| 同一微信再次绑定同一教师         | 返回已绑定状态；网络重试不生成新账号或重复关系       |
| 微信已绑定 A，邀请指向 B         | 阻止覆盖，提示联系班主任核对；不得自动切换或合并     |
| 教师账号已绑定其他微信           | 进入账号恢复流程，普通邀请不能覆盖已有绑定           |
| 同名教师、同一真人存在多个旧账号 | 单独核验；涉及历史操作者的合并不在普通绑定事务中执行 |

若首批教师普遍存在跨班多账号，必须先确定“账号治理”或“微信关联多身份”的独立方案，再扩大试点；本稿默认方案不能满足这类教师的全部跨班使用。

## 5. 核心用户流程

### 5.1 新教师首次绑定

1. 班主任在本班教师管理中建立任课关系，生成小程序绑定邀请。
2. 后台展示目标教师、学科、班级、有效期和小程序码。班主任定向发送给教师。
3. 教师扫码或从受支持的小程序入口打开邀请，看到目标身份；尚未确认时不消费邀请。
4. 教师点击“微信登录”，小程序取得临时登录凭证，后端校验并返回绑定状态。
5. 教师点击“确认绑定”。后端同时校验微信身份、邀请用途/状态/时效、目标账号及任课关系。
6. 在同一原子业务操作中完成绑定和邀请消费，成功后签发系统会话，进入邀请对应课堂。
7. 如绑定已成功但响应丢失，再次登录可找回同一教师，不要求重新创建教师或再次消费旧邀请。

邀请建议沿用 24 小时有效期；重发后旧的未使用绑定邀请全部失效。邀请须支持单独撤销，不通过撤销教师任课关系代替撤销邀请。上述重发失效及单独撤销是新增要求。

邀请属于持有者凭证，被转发后存在他人先行绑定的风险。建议首期采用“班主任定向发放 + 教师确认 + 可撤销恢复”；若需要班主任二次确认，增加“待确认”状态且确认前不发业务会话。该选择为上线前产品决策，不能仅靠提示文案替代。

### 5.2 已有 Web 教师迁移

班主任为原有教师生成专用迁移邀请，始终指向原 `User.id`。已消费或过期的 Web 邀请不可再次使用；迁移不创建新教师，不复制积分和历史记录。成功后新旧端读取同一数据，原操作者身份及本人撤销权限保持一致。

旧 Web 会话可用于展示迁移入口，但首期不将持有旧链接视为足够的微信绑定证明。原邀请页面继续履行原用途，小程序绑定凭证不得被旧消费接口直接兑换成 Web 教师会话。

### 5.3 再次进入与切班

本地会话有效时校验并加载课堂；过期则通过现有刷新机制或新的微信登录恢复。刷新失败不得循环重试。用户主动退出后停留登录页，再次点击登录才恢复会话；退出不等同于解绑。

只有一个有效班级时直接进入；同一账号有多个有效班级时显示选择器，优先恢复仍有权限的上次班级。切换时清除学生选择、未提交表单、点名排除列表和旧实时订阅；未提交内容丢弃前确认。迟到的旧班级响应不得覆盖当前班级。

无有效班级显示“暂无可用班级”和“联系班主任”。账号停用时拒绝登录；关系撤销时停止相关读写并清除缓存。其他有效班级的恢复行为应与会话吊销方案一致。

### 5.4 解绑、换微信与误绑定恢复

普通“重新邀请”不能覆盖绑定。教师仍能登录时，建议提供需要重新校验身份的换绑申请；无法登录时由班主任发起人工核验请求。

核验完成后撤销旧绑定、相关恢复凭证与旧会话，断开实时连接，再发一次性恢复邀请；保留原教师账号和全部历史记录，记录操作人、目标、原因和时间。

班主任默认只管理本班关系。若目标账号关联其他班级或拥有班主任角色，不得由单个任课班级的班主任直接全局解绑；处理权限和核验责任人必须在首期实施前确定，不能虚构现有系统不存在的全局管理员。恢复失败须保持明确的旧/新绑定状态，不出现双重有效绑定。

## 6. 页面与功能需求

### 6.1 页面结构

| 页面          | 核心内容与操作                                                     |
| ------------- | ------------------------------------------------------------------ |
| 登录/邀请确认 | 微信登录、目标教师/学科/班级、确认绑定、邀请错误处理               |
| 课堂首页      | 当前身份与班级、学生搜索、只读座位图、积分入口、随机点名、远程喊话 |
| 积分事件面板  | 所选学生、事件类型、必要参数、原因、提交                           |
| 积分流水      | 全部/本人/已撤销、分页、详情、有权限的撤销                         |
| 远程喊话      | 自定义/指定学生、正文预览、播报次数、展示时长、近期记录与状态      |
| 我的          | 系统教师身份、绑定状态、隐私说明、退出、账号恢复入口               |

建议使用“课堂 / 记录 / 我的”底部导航，喊话作为课堂操作入口。常用入口在 1～2 次点击内可达；带参数的业务允许必要步骤。主要点击目标不小于等效 44×44px；适配刘海、安全区、软键盘、字体放大和小屏手机。文案只保留标题、动作、状态及可操作错误。

### 6.2 学生与座位

保留按姓名查找和点击座位选择学生；同名学生显示学号辅助辨认。无座位学生仍可搜索和操作；无布局时提供名单入口。必须覆盖全班学生，不能沿用只取前 100 条导致遗漏的实现限制。

座位只读，不迁移拖拽编辑。学生状态变化或座位更新后刷新；已被移出班级的学生不得继续提交。加载、空班级、无搜索结果、接口失败分别呈现，失败提供重试。

### 6.3 积分事件登记

迁移当前 19 类事件：迟到、校服、晚自习点名、班级噪音前三、作业未交、作业表扬、年级考试前十、单科前三、突破性成绩、进步名次、卫生事件、寝室卫生、班委任务完成、黑板报、个人活动、团体活动、运动会决赛、活动违规、自定义事件。

支持单个或多个本班学生；按事件显示迟到分钟、名次、最终分值、组织者、特殊贡献、原因等必要字段。条件、取值范围和计算以现有事件服务及 DTO 为准；不能把旧“自定义积分至少 10 字”的设计直接套用到全部新事件。具体校验矩阵在接口评审时从现有 DTO/服务逐项固化，不另造计算公式。

提交中禁用重复操作；成功后刷新相关数据，显示“已记录”。失败保留表单。超时或响应丢失属于“结果待确认”，先核查记录，不能自动再次提交。多学生操作不得静默出现部分成功；沿用服务端事务语义并展示真实结果。

新增验收要求：同一次操作在重复点击、重试和双端并发下最多生效一次。若现有接口缺少幂等键和结果查询，须先补齐契约；按钮禁用不能替代服务端幂等。

### 6.4 流水与撤销

保留现有筛选及详情信息，通过分页访问完整历史，不能将前 100 条称为全部记录。本人记录依据系统用户 ID 判断。任课教师只撤销本人可撤销的记录，班主任权限仍由后端决定。

撤销前确认；已撤销记录和撤销记录本身不可再次撤销。双端同时撤销时只生效一次，另一端刷新为已撤销。历史 Web 记录在迁移后仍归原教师。首期保持逐条撤销语义，不隐式新增“撤销整个多学生事件”。

### 6.5 随机点名

服务端决定最终学生，小程序动画只表达过程和结果。保留当前轮次排除已点学生、候选耗尽后开启新轮次的体验；切班或重新进入后的轮次策略与 Web 对齐。

请求中禁止重复点名；接口失败停止动画并提示重试，不显示虚构结果。收到本次结果后可直接进入该学生积分操作。无座位学生正确展示姓名，不高亮无关座位。大屏和小程序以同一业务结果为准；重连补拉不重播已经结束的点名动画。

### 6.6 远程喊话

保留自定义及指定学生模式、1～100 字正文校验、1～5 次播报、10～180 秒展示设置、正文预览及播报时长校验。具体默认值和服务端限制沿用现有契约。指定学生无座位时允许发送并提示直接展示。

状态须区分“等待展示”“展示中”“已展示但语音异常”“已回复”“结束/超时/失败”；接口创建成功不等于大屏已展示或已播音。支持查看本人近期记录和主动结束，使用既有请求去重语义。

语音在大屏播放；小程序展示回执。大屏的输入暂停倒计时、回复竞争、教师结束和恢复状态等规则继续由原业务管理；小程序切后台不结束喊话。回到前台读取最终状态，不补发、不重新播报。首期不承诺在微信后台持续连接或收到系统级通知。

## 7. 数据、接口与实时边界

### 7.1 复用与新增

| 能力                                         | 处理原则                                                            |
| -------------------------------------------- | ------------------------------------------------------------------- |
| 学生、座位、积分事件、流水、撤销、点名、喊话 | 复用 `/api/v1` 下现有领域接口，按当前 Swagger/DTO/前端契约对齐      |
| 微信登录、绑定状态、绑定确认                 | 新增能力，路径和 Schema 待技术设计；登录返回已绑定/待绑定等最小状态 |
| 绑定邀请预览、重发、撤销                     | 扩展现有邀请领域，区别 Web 激活、首次绑定、恢复等用途               |
| 会话刷新、退出、鉴权                         | 复用现有会话体系；是否新增小程序 clientType 在技术设计确认          |
| 幂等操作及结果核查                           | 已有能力复用，缺失能力明确新增并测试，不假定所有写接口已支持        |
| 实时数据更新                                 | 适配现有 `/realtime`，保持班级范围和事件含义                        |

本文未列出的具体 URL、错误码、DTO 字段不视为已有接口。实施前补齐请求、响应、错误、权限、幂等键作用域和有效期；同时更新 mock、调用方与契约测试。

### 7.2 数据约束

建议新增微信身份关联及绑定/恢复审计数据，具有身份唯一性和并发约束；绑定凭证仅存安全摘要并限制时效/次数。邀请状态至少区分待使用、已使用、过期、撤销；如增加审批，再单独建待审批语义。

绑定、邀请消费和冲突校验必须具备事务/唯一约束保障；失败不留下已消费但不可登录的半成品。数据库变更同步 canonical/SQLite schema、迁移和生成流程；保留既有账号及积分引用，不迁移时重写历史操作者。

### 7.3 生命周期与实时通信

REST/数据库承载最终业务状态，实时事件用于及时通知与缓存失效。原生 WebSocket 连接成功不代表已支持 Socket.IO 协议；鉴权、namespace、订阅和重连必须整体验证。

进入前台时检查会话，刷新班级权限、学生、座位和进行中喊话；进入后台停止界面计时/无意义轮询；回前台建立新连接并补拉。去重事件，忽略旧班级响应；事务提交后才广播。

实时不可用时显示简短连接状态；允许安全的 REST 操作和手动刷新。若采用轮询降级，应明确频率、生命周期、流量与可接受延迟；不得宣称与实时同步等价。点名与喊话完整闭环未通过真机测试，不得以轮询列表可用作为全量迁移验收。

## 8. 异常、安全与隐私

| 场景                              | 预期结果                                                       |
| --------------------------------- | -------------------------------------------------------------- |
| 取消登录或未同意必要隐私流程      | 保持未登录，可重新操作，不创建教师或消费邀请                   |
| 微信临时凭证失效/微信接口暂不可用 | 获取新凭证后由用户重试；不无限重放旧凭证                       |
| 邀请过期、撤销、已使用            | 展示明确状态及联系班主任重发入口；同身份已成功绑定时可正常登录 |
| 两个微信同时消费同一邀请          | 仅一个成功，另一个无业务权限，不能覆盖成功者                   |
| 绑定完成但网络断开                | 下次登录恢复已绑定账号，不要求新建账号                         |
| 积分/喊话请求超时                 | 标记待确认，查结果；不把未知状态显示成成功或再次自动写入       |
| 账号停用、任课关系撤销            | 后端拒绝读写，清缓存、断订阅；不得只隐藏入口                   |
| 无网络或缓存过旧                  | 禁止写入；不排队在恢复网络后自动执行课堂操作                   |
| 大屏离线或声音被阻止              | 显示服务端回执状态，不承诺播音完成                             |

小程序只缓存必要会话和短期页面数据，退出/失权时清除学生与班级缓存。日志不记录完整 token、邀请凭证、OpenID 或学生名单；审计使用内部标识并限制访问。发布前明确数据用途、保留期限、查询/删除与账号恢复渠道。解绑不删除历史教学记录，账号注销及法定留存由独立数据政策确定。

平台发布依赖包括 AppID、服务端密钥配置、正式请求/Socket 域名、隐私指引、测试账号和审核材料；由发布负责人按当时微信后台及官方要求核验。开发工具关闭域名校验后的成功不能作为真机发布证明。

## 9. 技术方案建议与验证门槛

建议在 monorepo 新增独立小程序包，采用 Taro 4 + React 18 + TypeScript；锁定通过验证的具体版本，保留 Web 的 React 19。Taro 官方文档说明 React 18 为默认版本，但这不是本仓库组合已经兼容的证明。[Taro React 18](https://docs.taro.zone/docs/react-18)

共享纯类型、映射及与平台无关的业务逻辑；UI、路由、存储、请求和实时客户端按端实现。不直接复用 DOM、Ant Design、`window`、`localStorage` 或浏览器版 Socket.IO 初始化代码，不因迁移修改无关 Web 功能。

技术预研必须完成：微信登录 → 邀请绑定原教师 → 获取系统会话 → 获取学生 → 登记事件 → 查询流水 → 撤销 → 点名同步大屏 → 喊话回执 → 切后台再恢复。覆盖 iOS、Android 真机及正式域名设置。Taro 无法满足时再评估原生 TypeScript，不在预研前宣称框架最终锁定。

## 11. 验收标准与指标

### 11.1 必须通过的验收

| 编号 | 用例            | 通过条件                                                    |
| ---- | --------------- | ----------------------------------------------------------- |
| A01  | 新教师首次扫码  | 确认前不消费；绑定后为指定教师和班级，未增加重复教师        |
| A02  | 老教师迁移      | 原 User ID、历史流水及本人撤销权限保持一致                  |
| A03  | 再次登录/换设备 | 同一微信回到同一身份，无需新邀请；退出不会立即自动重新登录  |
| A04  | 邀请并发与重放  | 多端仅一次成功；过期/撤销/旧邀请无权绑定；响应丢失可恢复    |
| A05  | 身份冲突        | 微信已绑定其他账号、教师已绑其他微信均不被覆盖              |
| A06  | 权限与切班      | 修改 classId/studentId 不越权；旧班级缓存/响应不污染新班级  |
| A07  | 学生与座位      | 超过 100 名学生仍可完整访问；同名、无座位、停用学生正确处理 |
| A08  | 积分事件        | 19 类事件与现有后端结果一致；多学生、参数缺失及边界输入覆盖 |
| A09  | 写操作去重      | 连点、超时重试、双端操作不重复计分；未知结果可核查          |
| A10  | 流水与撤销      | 分页完整；本人识别正确；越权/重复撤销拒绝；历史归属不变     |
| A11  | 点名            | 服务端、小程序、大屏结果一致；无座位不误高亮；失败不造结果  |
| A12  | 喊话            | 展示、声音异常、回复、结束及离线分别可辨；切后台不重复发送  |
| A13  | 会话失效与恢复  | 关系撤销/账号停用立即阻断后续 API；重登录不恢复已撤销权限   |
| A14  | 换绑恢复        | 旧凭证失效、新绑定唯一；多班级账号无越权全局重置            |
| A15  | 双端回归        | Web 教师端、班主任后台、大屏现有业务正常，共享数据一致      |
| A16  | 真机发布        | iOS/Android、弱网、前后台、正式域名、软键盘和安全区验证通过 |

### 11.2 建议试点目标（待确认）

- 样本建议不少于 2 个班级、5 名教师、连续 5 个教学日，包含新教师和存量教师。
- 在正常网络且微信服务可用时，已绑定用户从打开到课堂可操作的 P95 ≤ 3 秒；服务端写入结果反馈 P95 ≤ 2 秒，点名动画耗时单独统计。
- 有效邀请绑定成功率 ≥ 99%，明确排除用户取消、过期和身份冲突并单独统计其原因。
- 重复计分、错误身份绑定、越权访问为 0；严重缺陷未清零不扩大试点。

记录登录、绑定、首次课堂操作、写入结果、实时恢复等必要事件，以不含敏感正文的内部标识关联。统计口径、网络条件和样本量随验收报告一起提交，不能将上述目标写成现有性能结论。
