# 轻量化架构与迁移评估

评估日期：2026-09-16  
评估分支：`codex/pr-1-integration`

## 当前架构

项目已统一为 Vite + React 静态 SPA、Elysia + Node.js API、Prisma SQLite 和 Socket.IO。OpenResty 托管 `apps/web/dist`，将 `/api/v1` 和 `/socket.io/` 代理到单个 Elysia 实例；SQLite 文件和 Redis 仍由服务端使用。

旧的服务端和前端源码、构建产物、环境变量兼容层和 workspace 引用已从当前分支移除。运行时不再需要旧框架进程，也不再需要前端 Node 常驻服务。

## 收益与边界

- 前端发布边界变为静态文件，减少一个常驻进程和对应镜像。
- 后端保留现有认证、班级权限、事务、积分、设备绑定和 Socket.IO 协议，避免业务层重复迁移。
- Vite 构建成功，但 `admin-pages` 仍有约 685 kB 的压缩后 chunk；这是后续拆包项，不是发布阻断项。
- 不能仅凭框架名称推断常驻内存收益，需用同一业务负载比较容器内存、冷启动、导入峰值、Socket 数和 SQLite 查询耗时。
- SQLite 单实例约束仍然存在；不能在未验证事务、会话、绑定码和实时广播前直接扩展为多实例。

## 数据库评估

服务器 SQLite 快照已经只读拉取并校验：远端与本地 SHA-256 一致，`integrity_check` 为 `ok`。当前服务器有 4 条已应用迁移；本地使用该副本演练后成功应用新增的 `20260911000000_add_usage_analytics_feedback`，因此数据迁移属于增量变更，风险低于重建或 `db push`。

正式切换仍必须先备份线上 SQLite，并在新实例启动前检查迁移结果、写权限和回滚副本。不能把本地开发用 PostgreSQL compose 当成生产数据库配置。

## 发布风险

当前服务器仍运行旧发布物，远端 compose 和静态目录尚未切换到本分支产物。因此“代码已清理”不等于“线上已迁移”。本地两个镜像已经构建并用迁移演练库完成启动、迁移和健康接口验证，但服务器资源仍不足以承担现场构建。

建议发布顺序：

1. 本地或 CI 构建并扫描后端、前端镜像。
2. 上传新产物，保留旧镜像、旧静态目录和 SQLite 备份。
3. 更新 compose 启动入口与静态根目录。
4. 启动新实例，执行迁移并检查健康接口。
5. 验收登录、邀请、学生、座位、课程表、积分、班委、随机点名、设备绑定和大屏实时反馈。
6. 观察日志和资源，再决定是否清理旧发布物。

本评估不授权也未执行线上迁移、重启、配置修改或发布。
