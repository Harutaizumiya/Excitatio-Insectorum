# 课序：使用状况分析与用户反馈功能 PRD

## 1. 文档信息

**功能名称：** 使用状况分析与用户反馈  
**适用端：** 学生大屏端、班主任后台、运营/管理后台  
**优先级：** P1  
**版本目标：** 第一阶段完成基础数据采集、问题反馈和管理侧查看能力。

---

## 2. 背景

课序当前包含面向学生展示的大屏端，以及面向班主任操作的管理端。

随着实际班级开始使用，需要建立统一的数据反馈机制，用于回答以下问题：

1. 大屏是否被持续实际使用；
2. 班主任主要使用哪些功能；
3. 哪些核心流程存在使用阻塞；
4. 当前版本是否存在高频异常；
5. 用户遇到问题后能否快速提交反馈；
6. 开发者能否根据反馈快速定位问题。

本功能用于建立“用户行为采集—异常记录—主动反馈—问题分析”的基础闭环。

---

## 3. 产品目标

### 3.1 核心目标

建立统一的使用状况采集与反馈体系，使管理者能够了解课序真实使用情况，并能够基于用户反馈和运行数据持续优化产品。

### 3.2 第一阶段目标

第一阶段重点实现：

- 学生大屏基础使用状态采集；
- 班主任后台关键行为事件采集；
- 前后端异常信息关联；
- 班主任主动反馈入口；
- 管理端查看基础使用数据；
- 管理端处理用户反馈。

第一阶段以可用、低侵入、易维护为主要原则。

---

## 4. 用户角色

### 4.1 学生

主要通过班级公共大屏查看课序内容。

学生通常不承担系统配置和管理职责，因此大屏端以自动采集运行情况为主。

### 4.2 班主任

课序主要管理用户。

班主任负责班级、学生、座位、积分、规则等相关操作，也是主要反馈提交者。

### 4.3 系统管理者 / 产品维护者

负责查看系统整体使用情况、异常情况和用户反馈，并根据数据决定后续产品优化方向。

---

## 5. 整体功能结构

功能整体分为四部分：

1. 使用事件采集；
2. 系统异常采集；
3. 用户主动反馈；
4. 数据分析与反馈管理。

不同客户端统一使用一套事件体系，并通过客户端类型进行区分。

建议至少区分：

- 学生大屏端；
- 班主任管理端；
- 其他后续扩展终端。

---

# 6. 学生大屏端使用状况采集

## 6.1 设计原则

学生大屏属于公共展示设备，采集应保持低干扰。

默认采用后台自动采集方式，不要求学生主动参与。

采集重点是：

- 是否正常运行；
- 是否持续在线；
- 哪些页面被展示；
- 是否发生异常；
- 页面性能是否正常。

---

## 6.2 基础运行事件

建议采集以下事件。

### 大屏启动

记录大屏应用成功进入主要展示页面。

建议记录：

- 班级标识；
- 客户端类型；
- 应用版本；
- 浏览器信息；
- 屏幕尺寸；
- 时间。

### 大屏在线状态

用于判断大屏实际运行时长。

系统可通过周期性心跳或其他机制记录大屏是否处于在线状态。

后续可统计：

- 单日在线时长；
- 连续在线时间；
- 异常中断次数；
- 不同班级的大屏活跃情况。

### 页面访问

记录当前展示页面或主要模块。

例如：

- 班级座位；
- 积分排行；
- 点名展示；
- 其他主要展示模块。

具体事件名称应根据实际产品结构定义。

---

## 6.3 大屏异常采集

建议记录：

- 页面加载失败；
- 接口请求失败；
- WebSocket 或实时连接异常；
- 自动重连次数；
- 页面脚本错误；
- 关键数据加载异常。

异常记录应尽量附带唯一的问题追踪标识。

该标识用于将：

用户反馈、前端异常、后端日志

关联到同一次问题。

---

# 7. 班主任后台行为采集

## 7.1 设计原则

班主任端的数据重点用于分析：

- 用户是否完成核心任务；
- 哪些功能高频使用；
- 哪些功能使用率低；
- 用户在哪一步产生失败或退出。

事件设计优先围绕“用户行为”展开。

避免记录大量无实际分析价值的点击行为。

---

## 7.2 建议核心事件

建议围绕现有核心业务逐步建立事件。

包括但不限于：

### 班级管理

- 创建班级；
- 进入班级；
- 切换班级；
- 修改班级设置。

### 学生管理

- 导入学生；
- 新增学生；
- 修改学生；
- 删除学生；
- 导入失败。

### 座位管理

- 进入座位编辑；
- 调整座位；
- 保存座位布局；
- 座位保存失败。

### 积分管理

- 新增积分记录；
- 批量积分操作；
- 修改积分记录；
- 积分操作失败。

### 排行榜

- 查看排行榜；
- 切换排行榜范围；
- 查看趋势信息。

### 教师管理

- 创建邀请；
- 教师加入班级；
- 教师退出班级；
- 取消教师授权。

### 积分规则

- 创建规则；
- 修改规则；
- 删除规则。

具体事件应根据实际已实现功能确定。

---

# 8. 事件数据模型

所有行为事件建议采用统一数据结构。

核心字段建议包括：

- 事件名称；
- 客户端类型；
- 用户角色；
- 班级标识；
- 用户或设备匿名标识；
- 当前应用版本；
- 发生时间；
- 执行结果；
- 页面或功能模块；
- Trace ID；
- 必要的扩展属性。

扩展属性用于不同事件携带少量业务信息。

例如：

导入学生事件可以记录：

- 导入人数；
- 成功人数；
- 失败人数。

积分操作可以记录：

- 单人操作 / 批量操作；
- 操作是否成功。

原则上避免直接上传完整业务数据。

---

# 9. 隐私与数据采集原则

行为分析数据主要服务于产品优化和故障分析。

默认避免采集：

- 学生真实姓名；
- 学号；
- 完整积分原因；
- 教师输入的自由文本内容；
- 其他不参与分析的个人信息。

如分析确实需要关联某个学生，可优先使用内部匿名标识。

管理后台展示的数据也应以聚合统计为主。

---

# 10. 用户反馈功能

## 10.1 入口

班主任后台提供统一“反馈”入口。

入口建议保证在主要页面均可访问，例如：

- 页面顶部操作区域；
- 用户菜单；
- 设置页面；
- 固定辅助入口。

具体呈现方式根据现有 UI 结构确定。

---

## 10.2 反馈类型

第一版建议提供：

- 功能异常；
- 操作困难；
- 数据问题；
- 功能建议；
- 其他。

用户选择一种类型后填写反馈。

---

## 10.3 反馈内容

用户填写：

- 问题描述；
- 可选截图。

系统自动补充环境信息。

建议包括：

- 当前功能模块；
- 当前页面；
- 应用版本；
- 浏览器信息；
- 客户端类型；
- 班级标识；
- 用户标识；
- 提交时间；
- Trace ID。

如有必要，也可以附带最近一次相关异常标识。

---

# 11. Trace ID 问题定位机制

Trace ID 用于建立用户反馈与系统日志之间的关联。

当用户执行一次重要操作时，系统可为该操作生成唯一标识。

该标识可贯穿：

客户端请求  
→ 服务端处理  
→ 日志记录  
→ 用户反馈

例如某次积分操作失败后，用户立即提交反馈。

反馈记录中包含该次操作的 Trace ID。

开发人员即可通过该标识定位对应日志。

该机制可以明显降低问题复现和沟通成本。

---

# 12. 反馈提交结果

用户提交后，应明确提示：

反馈已收到。

系统可以生成反馈编号，例如：

FB-20260911-0012

用户无需长期跟踪编号，编号主要用于内部问题定位。

如未来增加反馈进度查看功能，可继续沿用该编号。

---

# 13. 管理端反馈中心

## 13.1 反馈列表

管理者可以查看所有反馈。

主要信息包括：

- 反馈编号；
- 反馈类型；
- 来源端；
- 班级；
- 提交时间；
- 当前状态；
- 应用版本。

---

## 13.2 反馈状态

第一版建议：

- 待处理；
- 处理中；
- 已解决；
- 已关闭。

状态由管理者维护。

---

## 13.3 反馈详情

详情页展示：

用户提交内容：

- 问题描述；
- 截图。

系统上下文：

- 应用版本；
- 浏览器；
- 终端类型；
- 页面；
- 班级；
- Trace ID；
- 提交时间。

内部处理信息：

- 当前状态；
- 处理备注；
- 处理时间。

---

# 14. 使用状况分析页面

第一版的数据分析页面保持简单。

重点展示能够直接辅助产品判断的数据。

---

## 14.1 核心指标

建议提供：

### 活跃班级数

统计指定时间内发生有效行为的班级数量。

### 活跃教师数

统计指定时间内实际使用管理功能的教师数量。

### 大屏在线情况

包括：

- 当前在线大屏数量；
- 大屏平均在线时长；
- 最近一段时间的在线趋势。

### 反馈数量

显示：

- 新反馈；
- 待处理；
- 已解决。

---

# 15. 功能使用分析

展示主要功能使用情况。

例如：

| 功能 | 使用次数 | 使用班级数 |
|---|---:|---:|
| 积分操作 | - | - |
| 排行榜 | - | - |
| 随机点名 | - | - |
| 座位调整 | - | - |
| 学生管理 | - | - |
| 教师管理 | - | - |

核心关注“有多少班级使用了这个功能”。

单纯的点击次数容易受到高频用户影响。

---

# 16. 核心流程分析

后续可以逐步建立核心任务漏斗。

例如：

创建班级  
↓  
导入学生  
↓  
完成座位布局  
↓  
产生第一条积分记录  
↓  
持续使用

通过漏斗可以发现用户在哪一步大量流失。

第一版可以先保存完整事件数据，分析能力后续逐步增加。

---

# 17. 大屏运行分析

针对学生大屏单独提供基础运行状态。

建议统计：

- 已配置大屏班级数；
- 最近活跃大屏数量；
- 平均每日在线时间；
- 异常退出次数；
- 实时连接异常次数；
- 不同版本使用占比。

该模块重点用于判断大屏是否真正形成日常使用习惯。

---

# 18. 版本分析

事件和异常均需要携带应用版本。

管理者可以查看：

- 各版本活跃设备数量；
- 各版本错误数量；
- 某版本上线后的使用趋势；
- 错误是否集中于特定版本。

该能力对于后续快速迭代非常重要。

---

# 19. 异常监控

产品分析系统应能够结合前端和后端错误信息。

第一阶段可以使用成熟异常监控工具承担：

- 前端 JavaScript 异常；
- 网络请求异常；
- 服务端异常；
- 调用链追踪。

业务反馈仍保存在课序自身系统中。

推荐整体关系：

用户行为分析  
→ 产品行为分析平台

程序异常  
→ 错误监控平台

用户主动反馈  
→ 课序反馈系统

通过 Trace ID 或其他统一标识建立关联。

---

# 20. 数据留存

第一阶段建议保留原始事件数据，以便后续重新定义统计口径。

随着数据量增长，可以增加聚合统计机制。

例如：

原始事件  
→ 日级聚合  
→ 月级统计

高频数据可以保留较短周期。

业务反馈数据可以长期保留。

具体时间根据实际部署成本和业务规模调整。

---

# 21. 权限要求

学生大屏：

仅自动发送运行数据，不提供管理能力。

班主任：

可以提交反馈。

产品管理者：

可以查看整体统计和反馈。

系统管理员：

可以管理反馈状态和处理信息。

具体权限应沿用当前已有权限体系。

---

# 22. 非功能要求

## 性能

行为上报不能明显影响主要业务操作。

建议采用异步方式发送事件。

行为上报失败时，不影响用户正常使用主要功能。

---

## 稳定性

事件采集本身的异常不应导致业务页面出现错误。

必要时可以进行本地暂存和延迟上报。

---

## 扩展性

事件体系应允许新增事件。

避免为每一种事件建立独立数据结构。

建议通过统一事件模型 + 扩展属性实现。

---

# 23. 第一阶段 MVP 范围

第一阶段建议控制范围：

### 必须完成

- 学生大屏启动与在线状态采集；
- 教师端核心功能行为事件；
- 基础异常采集；
- Trace ID；
- 班主任反馈入口；
- 反馈管理页面；
- 活跃班级统计；
- 活跃教师统计；
- 大屏在线统计；
- 功能使用排行；
- 反馈数量统计。

### 后续迭代

- 用户行为漏斗；
- 用户留存分析；
- 班级生命周期分析；
- 自动异常聚类；
- 反馈与异常自动关联；
- 版本质量对比；
- 用户满意度调查；
- 产品运营报表。

---

# 24. 验收标准

功能上线后，应能够完成以下场景：

1. 管理者可以查看近期有多少班级真实使用课序；
2. 可以区分学生大屏和教师后台产生的数据；
3. 可以查看主要功能的实际使用频率；
4. 可以查看大屏运行和在线情况；
5. 班主任可以快速提交问题反馈；
6. 反馈能够自动携带必要的系统环境信息；
7. 发生异常时可以通过 Trace ID 辅助定位日志；
8. 管理者可以查看、分类并更新反馈处理状态；
9. 埋点或反馈系统异常不会影响核心业务功能；
10. 数据采集遵循最小必要原则，避免采集无关的学生个人数据。

第一版的核心价值是建立真实使用数据和问题反馈闭环。后续所有产品优化，都应优先基于实际行为数据、异常数据和班主任反馈进行判断。
